# Readiness checklist

In order: a later item often needs an earlier one. "Detect" says what counts as present, under any file name. "Fill" says how a missing item is produced.

| # | Item | Detect | Fill |
| --- | --- | --- | --- |
| 1 | **Base skills installed** | pstack is installed and is the version the kit pins: `lc-pstack check` exits 0 (in Claude Code, the plugin `pstack@cursor-plugins`). `grilling` and `domain-modeling` are among the available skills (the `mattpocock-skills` plugin). The Thermos audits and deslop come with the kit (`vendor/`) | Name the installs: `/plugin marketplace add cursor/plugins`, `/plugin install pstack@cursor-plugins`, `/plugin install mattpocock-skills@claude-plugins-official`. If `lc-pstack check` says pstack moved, stop and tell the owner: the fork must be brought up first. Then **stop**: the rest needs them |
| 1a | **pstack's models** | `~/.claude/rules/pstack-models.md` exists with a `# defaults: 3` line, every build role on `opus medium`, and `swarm workers: sonnet medium` | pstack's **setup-pstack** skill, budget small; then set the `swarm workers` line. The arena and interrogate lines stay: a critical brief uses them. It is the owner's machine file, not the repository's |
| 2 | **Docs set up for this repo** | An issue-tracker doc (`docs/agents/issue-tracker.md` or equal), a domain-docs doc (`docs/agents/domain.md`), and an "Agent skills" section in `CLAUDE.md` or `AGENTS.md` pointing to them | Write each with the person: where issues live (or `none`), the domain docs' paths; then the section pointing to them |
| 3 | **Product requirements (PRD)** | A doc stating what is built and for whom, under any name (`PRD.md`, `PRODUCT.md`, `docs/prd/`) | `grilling` with the owner, written as the PRD |
| 4 | **User stories** | Numbered stories stating the wanted behaviour, inside the PRD or beside it | `grilling` + `domain-modeling` (`shape-product`) |
| 5 | **User journeys** | Journeys that group the stories: each story belongs to at least one | `shape-product` |
| 6 | **Glossary** | `GLOSSARY.md`, or what the domain-docs doc names | `domain-modeling` |
| 7 | **Decision records** | The ADR folder the domain-docs doc names, with an index | `domain-modeling` creates it with the first decision |
| 8 | **Roadmap with stages** | A doc listing stages (its phases), each with its stories and state | `templates/roadmap.md`, filled with `shape-product` |
| 9 | **Current stage's acceptance criteria** | User outcomes, failure cases and invariants, numbered `<stage>-AC<n>`, agreed with the owner, in a file under `docs.acceptance` | `shape-product` with `templates/acceptance.md` |
| 10 | **Test rules** | A testing doc saying how flows are verified and which tests are written | `templates/testing.md`; on a clash with the existing doc, list it for the owner |
| 10a | **Verification skill** | A project skill (`docs.verification`, `.claude/skills/verify-<app>/`) with Launch, Doctor, Drive, Evidence and Cleanup, a feature map, and flow scripts its Drive section runs by one command; proven once end to end, and a planted break makes a script fail | pstack's **create-verification-skill**, as written. Then make each feature's proof a flow script (`browser`, or the public API or CLI): real sign-in, the result asserted, asserted again after a reload, no mocks. Each script names the acceptance criteria it decides (`<stage>-AC<n>`), so `lc-criteria` finds them |
| 10b | **Formal verification** | `docs.formal` names a project skill that runs a model checker by one command and has shown its property failing on a broken variant; or `none`, said by the owner | Ask: "Does the project have a state machine or a concurrent protocol where a wrong ordering is costly (retries, locks, leases, payments, lifecycle states)?" On yes, pstack's **create-formal-verification-skill**, as written (TLA+ and TLC through **statechart** for ordering questions); add `paths.formal`, `templates/ci/formal.yml` and `formal` to `ci.required_checks`. On no, `none` |
| 11 | **Verify profiles** | Five entry points (`verify:commit`, `verify:pr`, `verify:acceptance`, `verify:stage`, `verify:nightly`, or equal) that exist **and run**: run commit and pr, and record their time. `verify:pr` runs the flow scripts that cover the diff; `verify:acceptance` runs `lc-criteria` on the stage's acceptance file, then every flow script | Thin scripts over the commands the repo already has (`templates/ci/` shows the shape) |
| 12 | **CI on the profiles** | The PR workflow runs on every pull request, into a stage branch or the default branch, and calls the pr profile and the rules; a scheduled nightly calls the nightly profile and reports failures as an issue; a hand-started stage workflow runs the stage profile on a `candidate` input, with the candidate in its `run-name`, or the project states it has none. No CI host: `ci.enforcement: none` (the rest of the `ci` block deleted), and `gate_pr` command steps run the pr profile, and the rules, unless that profile runs them: that is the stage exit, and a pull request into a stage branch then has only the swarm's run lane, which re-runs the pr profile | `templates/ci/pr.yml`, `nightly.yml`, `stage.yml`; or ask "CI host, or none?" |
| 13 | **Review docs** | A code map naming each concept's owner and the sensitive paths (`paths.sensitive`) | From the repo's own rules, with pstack's **how** skill for what owns what |
| 13a | **Review question files** | The three files the stage exit names (`thermo-review.md`, `thermo-quality.md`, `stack-hunt.md`), each naming this repo's inputs and invariants | Copy them from `templates/review/` into the repo (for example `docs/review/`; the `stack-*` data files and `tool-fit.md` come in 14a) and fill in what each asks for. The Thermos rubrics themselves stay in the kit, unmodified |
| 13b | **Gate steps** | `gate_pr:` in the project file, each step's command, workflow or question file existing; `gate_pr_only: default-branch`; `paths:` for every `if`; no `here` step; `stage.branch` and `stage.plans` set; `lc-gate status pr <branch>` runs without an error (modes, hooks and CI come in 14a) | The block in `templates/project.yaml`, adapted with the owner: drop a step the project can't run yet only with the owner's yes, and say why in a comment |
| 14 | **Protected files, lanes, gate** | Protected files named (gate config or a doc); stack lanes named, or "no shared stack"; the gate configured, or stated as absent | Ask the owner; record pointers |
| 14a | **Enforcement** | `lc-gate enforcement --strict` exits 0: review route independent, stack files, CI templates, required checks and protection, protected rule files, modes | The Enforcement stage, [enforcement.md](enforcement.md); the owner decides on any host plan or setting change, recorded in `ci.enforcement` |
| 14b | **Mechanical rules** | `.agents/rules.yaml`, each rule naming a written decision; `lc-rules selftest` exits 0; `.agents/rules-baseline.json` written; both files in `protected_files`; the PR workflow and the `rules` step of `gate_pr` run `lc-rules check --base`. Or the owner states there are none yet | The Rules stage (SKILL.md step 6), `templates/rules.yaml`, the `rules` step of `templates/project.yaml` |
| 15 | **Session tooling** | `lc-spawn`, `lc-gate`, `lc-pstack` and `lc-criteria` on the PATH and runnable; the handoff directory exists with `plans/`, `kickoffs/`, `reports/` and `trails/`; the watchdog prompt (`templates/watchdog-prompt.md`) filled in for this project; `sessions.agent_flags` says how sessions get permissions unattended | `install.sh`; create the directory; fill the template into the handoff directory. Ask: "Sessions run unattended; how do they get permissions: `--permission-mode auto` (recommended), an allow-list in `.claude/settings.json`, or you answer each prompt?" |
| 15a | **Board** | `lc-board start` serves the page; it shows the roadmap's stages with their journeys, changes and criteria, the open PRs and the sessions; `board.port` and `board.data_dir` set or defaulted; `board.running_log` and `board.keeper_model` set for the keeper | `lc-board start`; fix the roadmap or journey index where the board finds nothing |
| 16 | **Project file** | `.agents/project.yaml` with every key a pointer or a literal, no `<…>` left | Built up item by item above |
| 17 | **Agent instruction files point to the lifecycle** | `AGENTS.md` and/or `CLAUDE.md` link the lifecycle doc and `.agents/project.yaml` | One line each; if they are protected, their own PR for the owner |
| 18 | **Lifecycle doc** | A way-of-working page with the ADLC order and which skill fires at each step | `templates/lifecycle.md`, with the diagram `docs/adlc.svg` beside it |
