# Readiness checklist

In order: a later item often needs an earlier one. "Detect" says what counts as present, under any file name. "Fill" says how a missing item is produced.

| # | Item | Detect | Fill |
| --- | --- | --- | --- |
| 1 | **Base skills installed** | `grilling`, `domain-modeling`, `code-review`, `tdd`, `diagnosing-bugs`, `pr`, `writing-for-agents`, `codebase-design`, `prototype`, `research` are among the available skills: the `mattpocock-skills` plugin in Claude Code, or `~/.agents/skills/<name>` for Codex | Name the install: in Claude Code, `/plugin install mattpocock-skills@claude-plugins-official`; for Codex, link the skills of a clone of `mattpocock/skills` into `~/.agents/skills`. Then **stop**: the rest needs them |
| 2 | **Base skills set up for this repo** | Their setup's outputs: an issue-tracker doc (`docs/agents/issue-tracker.md` or equal), a domain-docs doc (`docs/agents/domain.md`), a triage-labels doc if the `triage` skill is installed, and an "Agent skills" section in `CLAUDE.md` or `AGENTS.md` pointing to them | Write each with the person: where issues live (or `none`), the domain docs' paths, the labels; then the section pointing to them |
| 3 | **Product requirements (PRD)** | A doc stating what is built and for whom, under any name (`PRD.md`, `PRODUCT.md`, `docs/prd/`) | `grilling` with the owner, written as the PRD |
| 4 | **User stories** | Numbered stories stating the wanted behaviour, inside the PRD or beside it | `grilling` + `domain-modeling` (`shape-product`) |
| 5 | **User journeys** | Journeys that group the stories: each story belongs to at least one | `shape-product` |
| 6 | **Glossary** | `GLOSSARY.md`, or what the domain-docs doc names | `domain-modeling` |
| 7 | **Decision records** | The ADR folder the domain-docs doc names, with an index | `domain-modeling` creates it with the first decision |
| 8 | **Roadmap with phases** | A doc listing phases, each with its stories and state | `templates/roadmap.md`, filled with `shape-product` |
| 9 | **Current phase's acceptance criteria** | User outcomes, failure cases and invariants, numbered, agreed with the owner, in the roadmap or a linked file | `shape-product` with `templates/acceptance.md` |
| 10 | **Test rules** | A testing doc saying how flows are verified and which tests are written | `templates/testing.md`; on a clash with the existing doc, list it for the owner |
| 11 | **Verify profiles** | Four entry points (`verify:commit`, `verify:pr`, `verify:phase`, `verify:nightly`, or equal) that exist **and run**: run commit and pr, and record their time | Thin scripts over the commands the repo already has (`templates/ci/` shows the shape) |
| 12 | **CI on the profiles** | The PR workflow calls the pr profile and `lc-gate check phase --diff`; a scheduled nightly calls the nightly profile and reports failures as an issue; a hand-started phase workflow runs the phase profile on a `candidate` input, with the candidate in its `run-name`, or the project states it has none. No CI host: `ci.enforcement: none`, and `gate_pr` command steps run the pr profile and the rules | `templates/ci/pr.yml`, `nightly.yml`, `phase.yml`; or ask "CI host, or none?" |
| 13 | **Review docs** | A per-change review checklist; a code map naming each concept's owner and the sensitive paths; the phase-exit values (`docs.phase_review`: evidence commands, what the phase profile runs) and a folder for phase records (`docs.phase_records`) | The checklist and code map from the repo's own rules, with `codebase-design`; `templates/phase-review.md` for the values |
| 13a | **Review question files** | One file per review session the gates name (built as described, correctness, security, architecture, duplication, dead code, docs), each naming this repo's rules, paths and invariants | Copy the question files of `templates/review/` into the repo (for example `docs/review/`; the `stack-*` files, `tool-fit.md` and `stack-hunt.md` come in 14a) and fill in what each asks for from the repo's own docs |
| 13b | **Gate steps** | `gate_pr:` and `gate_phase:` in the project file, each step's command, workflow or question file existing; `paths:` for every `if`; no `here` step in `gate_pr`; its `reviewer` step on `docs.review_checklist` has no `if` (every PR); `lc-gate status pr <branch>` runs without an error (modes, hooks and CI come in 14a) | The blocks in `templates/project.yaml`, adapted with the owner: drop a step the project can't run yet only with the owner's yes, and say why in a comment |
| 14 | **Protected files, lanes, gate** | Protected files named (gate config or a doc); stack lanes named, or "no shared stack"; the gate configured, or stated as absent | Ask the owner; record pointers |
| 14a | **Enforcement** | `lc-gate enforcement --strict` exits 0: review route independent, stack files, git hooks, CI templates, required checks and protection, protected rule files, modes | The Enforcement stage, [enforcement.md](enforcement.md); the owner decides on any host plan or setting change, recorded in `ci.enforcement` |
| 14b | **Mechanical rules** | `.agents/rules.yaml`, each rule naming a written decision; `lc-rules selftest` exits 0; `.agents/rules-baseline.json` written; both files in `protected_files`; the `rules` step of `gate_pr` (or the PR workflow) runs `lc-rules check --base`; a decision no rule kind fits is a `(must-fix)` item of the review checklist. Or the owner states there are none yet | The Rules stage (SKILL.md step 6), `templates/rules.yaml`, the `rules` step of `templates/project.yaml` |
| 15 | **Session tooling** | `lc-spawn` and `lc-gate` on the PATH and runnable (with no arguments each prints its usage); the handoff directory exists with `briefs/` and `reports/`; the watchdog prompt (`templates/watchdog-prompt.md`) filled in for this project; `sessions.agent_flags` says how gate sessions get permissions unattended | `install.sh`; create the directory; fill the template into the handoff directory. Ask: "Gate sessions run unattended; how do they get permissions: `--permission-mode auto` (recommended), an allow-list in `.claude/settings.json`, or you answer each prompt?" |
| 15a | **Board** | `lc-board start` serves the page; it shows the roadmap's phases with their journeys, changes and criteria, the open PRs and the sessions; `board.port` and `board.data_dir` set or defaulted; `board.running_log` and `board.keeper_model` set for the keeper | `lc-board start`; fix the roadmap or journey index where the board finds nothing |
| 16 | **Project file** | `.agents/project.yaml` with every key a pointer or a literal, no `<…>` left | Built up item by item above |
| 17 | **Agent instruction files point to the lifecycle** | `AGENTS.md` and/or `CLAUDE.md` link the lifecycle doc and `.agents/project.yaml` | One line each; if they are protected, their own PR for the owner |
| 18 | **Lifecycle doc** | A way-of-working page with the ADLC order and which skill fires at each step | `templates/lifecycle.md`, with the diagram `docs/adlc.png` beside it |
